# Incident 1033 — `health-tracker.co.uk`, 2026-11-17

**Severity:** production down (apex + 8 service hostnames), ~2h (11:22–14:23 UTC).
**Status:** RESOLVED 2026-11-17 14:23 UTC. No DNS record changed.

---

## 1. Symptom

`https://health-tracker.co.uk` returned HTTP **530** with body
`error code: 1033` (owner report, ray `a5bf256dac705e1d`, 13:40:15 UTC).
`www`, `test`, `tui`, `mc`, `omb`, `agenda`, `tgtg`, `dsh` were all 530 too.

**1033 means "this hostname is routed to a Cloudflare Tunnel and no connector is
attached to it."** It is not a DNS problem, not a 5xx from our app, and not an
edge problem: the CNAME resolves and Cloudflare is healthy.

## 2. Root cause

| Fact | Measured |
|---|---|
| Apex CNAME | `d9f81831-7d2b-4156-85ac-626f085d0cd3.cfargotunnel.com`, proxied |
| Tunnel `id-vps-tunnel` `d9f81831…` | status **`down`, 0 connections** |
| Origin host `103.147.32.117` (`standar-c3r3a-1845`) | ping OK; **:22 and :20133 refused**; `:80` answered a hosting-provider shared-IP landing page ("Alamat IP publik bersama / Domain belum terhubung"), i.e. not our app |
| `prod-studio-tunnel.service` (this dev box, tunnels `:18788` to that host) | failing since **2026-11-17 11:22:29 UTC**, 7,700+ restarts, `ssh: connect to host 103.147.32.117 port 20133: Connection refused` |

The VPS that ran the only connector for `d9f81831` disappeared at ~11:22 UTC and
its IP was re-assigned by the provider. With no connector, every hostname on
that tunnel answered 1033. The app itself was never broken — it kept serving
correctly on `VM-0-6-ubuntu` the whole time.

## 3. Fix

The tunnel **token for `d9f81831` was still valid** (readable with the
account/zone token in `~/.cloudflared/cert.pem`), so recovery did not need a DNS
edit — only a connector on a reachable host:

1. Installed credentials `root:root 600` at
   `/etc/cloudflared/d9f81831-7d2b-4156-85ac-626f085d0cd3.json` on
   `VM-0-6-ubuntu` (`43.173.42.248`).
2. Wrote ingress `/etc/cloudflared/config-id-vps.yml`: apex → `127.0.0.1:80` and
   wildcard → `127.0.0.1:80`, fallback `http_status:404`.
3. Added `cloudflared-id-vps.service` (root, `Restart=always`, enabled) and
   started it. It registered **4 connections** (sin11, sin19 ×2, sin14) and the
   tunnel went `healthy`.
4. Brought the deploy clone from stale `77be1d13` (2026-11-06) to
   `origin/main` `6b3d8010` via `/home/ubuntu/deploy.sh` and restarted the
   service — the stale clone was 18 commits behind, including the meal-history
   401 fix.
5. Stopped and disabled `prod-studio-tunnel.service` on the dev box: it existed
   only to reach the dead VPS and was looping 7,714 restarts.

## 6. Prevention

The failure mode is "the single connector host goes away silently". Standing
gaps to close:

- `cloudflared-id-vps.service` has `Restart=always`, but nothing alerts when the
  tunnel goes `down` at the API level. A cheap watcher should poll
  `GET /accounts/{acct}/cfd_tunnel/d9f81831…` and alert when `status != healthy`.
- `docs/infra/DOMAINS.md` named a host nobody could reach for a day; it now names
  `VM-0-6-ubuntu` and its unit/config paths.
- `docs/agent/WORKTREES.md` still documents `root@103.147.32.117:20133`. Retire
  that entry with the VPS retirement record.
