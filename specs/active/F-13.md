# Packet: Case-12 T2 — same-thread meal edit (add/remove)

Human replies: **go** | stop | one comment. Nothing below is applied yet.

## Journey

Better = after a logged meal, the user reopens the meal sheet and types a follow-up
("add oats, drop the coconut") and the app **edits that meal** — oats added, coconut
gone, column sums equal the meal totals — instead of silently starting a fresh
`review` thread that double-counts.

## Findings (do not redo — verified by reading, not guessing)

1. **The sheet closes on submit by design.** `onJobEnqueued` (`src/App.tsx:7783`) sets
   `activeJobId = null`; `isFoodChatOpen` (`src/App.tsx:1602-1608`) is *derived* from
   `activeJobId`, so the modal unmounts. The comment there already claims
   *"follow-up edits reopen it"* — **nothing implements that reopen.** The intent is
   documented; the implementation is missing.
2. **Reopening always creates a brand-new job.** Quick action "Catat Makanan" →
   `onLogMeal` (`src/App.tsx:6599`) unconditionally `JobStore.createJob(...)` + 
   `setActiveJobId(newId)`. So `jobId` is a **blank draft**.
3. **A blank draft ⇒ `review`.** `LogChat.tsx:2070` computes `hasPriorResult` from that
   blank draft ⇒ false ⇒ `submissionMode = 'review'` (line 2076-2077). No `activeMeal`
   is attached, so the add/remove intent is lost.
4. **Auto-bind cannot rescue it.** The two auto-bind effects (`LogChat.tsx:964-990` and
   `992-1008`) only run when `!jobId`, and both filter `!j.savedToLog && !j.viewed`.
   After **Save Log** the just-logged job is excluded by construction.
5. **Why T1 and T2 must differ** (this is the crux and the reason a naive
   "always adopt the newest meal" fix is wrong): T0 setup already leaves a *succeeded*
   food job before T1 runs. So "adopt the most recent meal" would turn **T1 itself**
   into an edit of T0's coconut row and break the currently-green T1. The correct
   discriminator already exists in the codebase's own idiom (`LogChat.tsx:2071`):
   **`finalImages.length`**. T1 sends a photo ⇒ new scan. T2 sends no image ⇒ follow-up.
6. Lock-merge (recorded gap 3): at `server_dish_finalize.ts:285-289` / `317-322` a
   `per_100g` lock scales `v * (consumedWeight/100)`, but the residual fill
   (`:330-336`) uses `effectiveR = brandCal/scoutCal` for brand locks — a **different
   basis** than the lock, which is what produces "partially merged / inconsistently
   scaled macros + wrong Atwater flag" (400 kcal @ 40 g).
7. Recorded, **out of scope here** (see `correct_results.md` gaps 1-3): `previous_meal`
   tag carries nutrients verbatim at tag weight (no rescale); `brand_menu_local_*` ids
   never resolve in `getBrandMenuItemById`.

## Plan

1. **Same-thread follow-up (LogChat only — `App.tsx` stays frozen).**
   In the `isAgent('food')` submit block, when the current job is a **blank draft**
   (no result, no messages) **and** a recently succeeded food job exists **and**
   `finalImages.length === 0` **and** the text carries no fresh-scan intent, adopt that
   prior job as the edit target: submit with `mode: 'edit'` and its `activeMeal`.
   Done when: a text-only follow-up after Save Log reports `mode === 'edit'` and the
   prior meal's ids/dishes are carried as `activeMeal`.
2. **Lock-merge basis consistency (`server_dish_finalize.ts`).**
   Make the residual fill use the **same basis** as the applied lock: when
   `dbSource === 'brand_official'` and `brandLock.basisType === 'per_100g'`, scale
   residuals by `consumedWeight / 100` instead of `brandCal / scoutCal`.
   Done when: a `per_100g` lock at a non-100 g consumed weight yields all keys on one
   basis and `atwaterFlag.flagged === false` for a self-consistent row.
3. Unit-test both in `server_dish_finalize.test.ts` / the composite contract test.
   Done when: new cases assert the scaler + the T1/T2 discriminator as pure functions.
4. Re-run the live T2 gate (`LIVE_MEAL12=1`). Done when: T2 green
   (3 dishes, `Mr Oat Rolled Oats` present, no `Coconut`, oats 40 g, column sums ==
   totals) with T0/T1 **still** green.
